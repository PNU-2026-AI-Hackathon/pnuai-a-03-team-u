### ① 과제 선정 배경 · Background — 13.9cm

> 서식 원래 소제목은 "개발 배경". 공지 "나" 항목에 따라 수정 가능.

**형식**: 번호 붙인 4문장 (체언 종결형) + 정량 근거 2개는 큰 숫자로 강조

1. 학사·비교과·취업·자격증 정보가 학지시·수강신청·포털 등 **여러 시스템과 외부 사이트에 분산**되어, 학생이 자신의 학업 현황을 한 번에 파악하기 어려움
2. 졸업요건·이수학점·필수과목 확인·계산이 어렵다는 응답 **63.4%**(재학생 설문 N=93), 복수전공·부전공자는 요건이 중첩되어 부담 가중
3. 매 학기 수강 계획 수립이 어렵다는 응답 **44.1%**, 장기 로드맵 없이 학기 단위 임기응변식 수강신청 반복
4. 학생지원시스템·산지니 AI는 정보 조회와 범용 AI 활용에 초점, 개인의 **이수내역·졸업요건·다중전공을 구조화해 수강계획을 설계하는 도구 부재**

**디자인 지시**: 2·3번의 `63.4%` / `44.1%`는 문장 안에 묻지 말고 100~140pt 큰 숫자로 따로 띄울 것. 이 프로젝트의 유일한 정량 근거임.

> **설문 출처**: 부산대 재학생 설문 N=93 (대학 생활 정보 관리 실태 설문조사)
> - 63.4% = 졸업요건·이수학점·필수과목 확인·계산이 어렵다
> - 44.1% = 수강 계획 수립이 '어렵다'(38.7%) + '매우 어렵다'(5.4%)
> - '보통이다'(35.5%)까지 더하면 79.6%(5명 중 4명) — **배너에는 44.1%만 쓸 것.** '보통'을 어려움으로 집계하면 심사에서 지적받을 수 있다.

### ② 과제 목표 · Objectives — 11.1cm

> 서식 원래 소제목은 "문제 정의". 배경과 내용이 겹쳐 "과제 목표"로 교체.

**형식**: 기능명 리드인 + 설명 4문장. 배경 4개와 1:1로 대응.

1. **내 정보 확인** — 학지시 크롤링으로 학적·성적·이수내역을 **자동 수집·통합**해, 흩어져 있던 학업 현황을 한 화면에서 확인
2. **다중 졸업요건 분석** — 주전공·복수전공·부전공 요건을 **규칙 기반 검증 엔진**으로 각각 판정하고 중복 인정까지 반영해, 이수구분별 남은 학점 자동 산출
3. **성장 로드맵** — 남은 요건·진로 목표를 반영한 **1~4학년 학기별 수강 계획을 AI 상담으로 설계**, 사용자가 승인한 항목만 반영(Human-in-the-loop)
4. **시간표 AI 추천** — 확정된 로드맵을 **실제 개설 분반(요일·교시·교수)과 대조**해 충돌 없는 다음 학기 시간표 후보 추천

**배경 ↔ 목표 대응표** (디자인에 반영할 것)

| ① 과제 선정 배경 | ② 과제 목표 |
|---|---|
| 1. 정보 분산 | → 1. 내 정보 확인 |
| 2. 졸업요건 계산 부담 (63.4%) | → 2. 다중 졸업요건 분석 |
| 3. 수강 계획 어려움 (4명 중 3명) | → 3. 성장 로드맵 |
| 4. 기존 도구 공백 | → 4. 시간표 AI 추천 |

**디자인 지시**: ①과 ②를 좌우 2열로 마주 보게 배치하면 이 대응 관계가 그대로 시각화됨. 문제 하나하나에 답이 달려 있는 구조로 읽힘.

### ③ 해결 방안 · Solution — 32.6cm (최대 영역)

**형식**: 한 줄 정의 + 파이프라인 다이어그램 + 스크린샷

한 줄 정의 (대형):
> **모으고 → 판정하고 → 제안한다**

파이프라인 다이어그램 (가로 6단계):
```
학지시 크롤링 → 이수내역 DB → 규칙 기반 졸업요건 판정 → LLM 상담 에이전트 → 학기별 성장 로드맵 → 시간표 후보
```

강조 배지:
> **판정은 규칙 엔진, 설명·추천은 LLM** — 정확성이 필요한 졸업요건 판정은 결정론적 규칙 엔진이, 자연어 설명과 우선순위 제안은 LLM이 담당

### ④ 핵심 기능 · Key Features — 29.3cm

> 서식의 "소제목 입력" 자리. 영문 라벨은 현재 `Solution`.

> **⚠ ② 과제 목표와 항목이 동일하다. 역할을 반드시 나눌 것.**
> - **상단 ② 과제 목표** = 무엇을 이루려는가 → 텍스트만, 문장 위주
> - **하단 ④ 핵심 기능** = 어떻게 구현했는가 → **스크린샷이 주인공**, 문장은 짧은 캡션으로 축소
>
> 같은 4개를 두 번 읽히는 게 아니라, 위에서 약속하고 아래에서 증명하는 흐름이 되어야 한다.

**형식**: 실제 화면 스크린샷 4장 + 짧은 캡션

| # | 기능 | 설명 |
|---|---|---|
| 1 | **내 정보 확인** | 학지시 크롤링으로 학적·성적 자동 수집, 이수구분별 남은 학점 자동 계산 |
| 2 | **성장 로드맵 (AI 상담)** | 남은 요건·진로 목표를 반영해 학기별 수강 계획을 대화로 설계 |
| 3 | **시간표 추천** | 확정된 로드맵을 실제 개설 분반(요일·교시·교수)으로 구체화 |
| 4 | **다중전공 지원** | 주전공 / 복수전공 / 부전공 요건을 각각 반영 |

강조 배지:
> **Human-in-the-loop** — AI는 DB를 직접 수정하지 않는다. "이 변경을 반영할까요?" 형태로 제안하고, **사용자가 승인한 항목만** 반영된다 (생성·수정·삭제 모두 동일)

### ⑤ Technical Overview — 20.6cm

**형식**: 가로형 아키텍처 다이어그램 + 기술 배지 줄

```
[Frontend · Netlify]           [Backend · Railway]                     [DB · Supabase]
React 19 + Vite + TS   →     FastAPI + SQLAlchemy + Alembic      →    PostgreSQL 17
JWT 인증                      · REST API                                + pgvector
                              · 규칙 기반 졸업요건 검증 엔진
                              · LangChain tool-calling 에이전트
                              · Playwright 크롤러
```

> 서비스는 Netlify(프론트엔드)와 Railway(백엔드)에 배포되어 있다.

기술 배지 줄:
`React 19` `Vite` `TypeScript` `FastAPI` `SQLAlchemy` `Alembic` `LangChain` `gpt-5.4-nano` `Supabase` `pgvector` `Playwright`

보안 한 줄 (24pt):
> **포털 자격증명 비저장**(동기화 처리에만 사용) · 로그인 비밀번호 **bcrypt 단방향 해시** · 외부 LLM 호출 시 개인 식별정보 **비식별화**

> 학생지원시스템 자격증명은 동기화 요청 처리에만 사용하며 저장하지 않는다.

## 6. 인쇄 전 검수 체크리스트

- [ ] 화면에서 **25%로 축소**해도 본문이 읽히는가 (= 실물 1~2m 거리 가독성)
- [ ] 슬라이드 크기가 60×90cm 그대로인가
- [ ] 로고 3개의 위치·크기·비율이 원본 그대로인가
- [ ] 폰트가 맑은 고딕 / Arial인가 (다른 폰트를 썼다면 "파일에 폰트 포함" 저장 필수)
- [ ] 모든 이미지가 150dpi 이상인가 (확대했을 때 깨지지 않는가)
- [ ] 1장 하단과 2장 상단이 이어졌을 때 어색하지 않은가
- [ ] 스크린샷에 개인정보가 노출되지 않았는가
- [ ] 오탈자 — 팀원 전원 교차 확인
- [ ] 섹션 ② 영문 라벨이 `Problem` → `Objectives`로 수정됐는가
- [ ] 섹션 ③ 영문 라벨이 `Problem` → `Solution`으로 수정됐는가
- [ ] ② 과제 목표와 ④ 핵심 기능이 같은 문장을 반복하고 있지 않은가
