# AI 활용 내역

Plan-U 개발 과정에서 활용한 AI 도구, 활용 범위, AI가 생성한 코드의 검증·수정 방식을 정리한다.

## 1. 활용한 AI 도구

| 도구 | 성격 | 용도 |
|---|---|---|
| **Claude Code**(Anthropic, Claude Max 요금제) | AI 페어 프로그래밍 에이전트 | 팀 전체의 주력 개발 도구. 백엔드/프론트엔드/데이터 파이프라인/문서를 실제 파일시스템·터미널·DB에 직접 접근해 작업. Max 구독료는 팀 공동 경비로 부담 |
| **Cursor**(Anysphere) | AI 코드 에디터 | 프론트엔드 화면 작업처럼 인라인 diff를 보면서 빠르게 반복하는 작업에 병행 사용. Claude Code/Codex처럼 별도 API 키가 아니라 자체 구독으로, 이 역시 팀 공동 경비 |
| **Codex**(OpenAI) | AI 페어 프로그래밍 에이전트 | 팀원 간 작업 분담 시 병행 사용(예: 학과별 교육과정 원문 수집처럼 병렬화 가능한 조사 작업을 도구별로 나눠 진행) |
| **Figma MCP** | 디자인 연동(MCP 서버) | 필요할 때 Figma의 변수·컴포넌트 사양을 조회해 색상·간격 등 디자인 토큰을 코드와 대조 |
| **Notion MCP** | 협업 문서 연동(MCP 서버) | 필요할 때 팀 기획·회의 기록을 조회해 요구사항과 결정사항을 코드·문서 작업에 반영 |
| **gpt-5.4-nano**(OpenAI) | **제품 런타임 기능** | 로드맵·시간표 AI 상담 에이전트의 기본 응답 생성 모델. 골든 평가의 도구 호출 성공률·시나리오 충족 여부·지연시간을 함께 검토해 기본값으로 설정 |
| **text-embedding-3-small**(OpenAI) | 선택적 검색 기능 | 교육과정 문서 임베딩용. 현재 기본 검색은 구조화 DB 필터를 사용하며, 벡터 검색은 필요 시 활성화한다. |

Claude Code/Cursor/Codex/Figma MCP/Notion MCP는 **개발 과정의 도구**이고, gpt-5.4-nano/text-embedding-3-small은 **서비스 자체에 내장된 기능**이라는 점을 구분한다. 아래 2·3절은 전자(개발 도구로서의 AI 활용)를 기준으로 서술한다.

### 왜 이 조합을 선택했는지

**개발 도구(Claude Code/Cursor/Codex)**
- 5인 팀이 짧은 기간에 크롤러 재실행, 카탈로그 정합성 보정, DB 조회, 화면 구현을 병행해야 했기 때문에 코드 작성뿐 아니라 파일·터미널 작업을 보조할 수 있는 에이전트를 활용했다.
- 작업 성격에 따라 도구를 나눴다. 인라인 diff를 보며 화면을 반복 조정할 때는 Cursor를, 터미널·다중 파일·데이터 작업에는 Claude Code와 Codex를 주로 사용했다. 병렬화 가능한 조사·정리 작업은 팀원이 나눠 진행했다.
- 개발 에이전트의 도구 접근은 작업자가 승인한 개발 환경과 필요한 범위로 제한했다. 운영 데이터 변경이나 배포처럼 영향이 큰 작업은 팀원이 검토하고 실행했다.

**MCP 연동(Figma / Notion)**
- Figma MCP는 디자인 토큰과 컴포넌트 사양을 확인할 때, Notion MCP는 기획·회의 기록을 확인할 때 선택적으로 사용했다. 외부 도구에서 읽은 값이나 문서는 그대로 적용하지 않고, 화면·코드·최신 결정사항과 다시 대조했다.

**제품 런타임(gpt-5.4-nano / text-embedding-3-small)**
- gpt-5.4-nano는 로드맵·시간표 상담의 기본 모델이다. 모델·프롬프트 변경은 골든 시나리오를 반복 실행해 도구 호출, 시나리오 충족, 지연시간을 함께 관찰한 뒤 반영한다. LLM 응답은 확률적이므로 단일 실행 결과나 한 가지 지표만으로 우열을 단정하지 않는다.
- 반복 평가는 기본적으로 동일 시나리오를 3회 실행한다. 실행 이력과 세부 결과는 Langfuse의 `planu-golden-v1` 데이터셋 및 GitHub Actions의 주간 평가 워크플로에서 확인한다. 이 평가는 품질 추이를 관찰하는 용도이며, 자동 병합 차단 기준으로 사용하지 않는다.
- text-embedding-3-small은 교육과정 문서의 선택적 벡터 검색을 위한 임베딩 모델이다. 현재 기본 검색은 학과·학년·이수구분 기반의 구조화 DB 필터를 사용하며, 벡터 검색은 강의계획서 같은 자유 텍스트 검색을 확장할 때 활성화한다.

## 2. 활용 범위

- **코드 생성**: FastAPI 라우터, SQLAlchemy 모델, Alembic 마이그레이션, React/TypeScript 프론트엔드, pytest 테스트 코드 전반.
- **데이터 파이프라인**: 수강편람·졸업요건 원문(One-Stop 포털, 학과 홈페이지 HWP/PDF/AIS 위젯 등)을 수집하는 크롤러(Playwright 기반), 파서, 정규화 스크립트.
- **디자인 연동(Figma MCP)**: Figma 파일의 색상·간격·타이포그래피 사양을 CSS/디자인 토큰과 대조. 반영 후에는 렌더링된 화면을 다시 확인.
- **협업 문서 연동(Notion MCP)**: 필요 시 회의록·기획 결정 사항을 조회하고, 적용 전 최신 결정과 충돌하지 않는지 팀원이 확인.
- **문서화**: README, `docs/CHANGELOG.md`, 기능 문서(`docs/backend/features/`), PR 설명, 이 문서를 포함한 제출 문서.
- **디버깅/장애 대응**: 배포 후 회귀(예: 마이그레이션 누락으로 인한 회원가입 실패)를 실시간으로 진단하고 복구.
- **코드 리뷰**: 아래 3절 참고.

**규모 참고**: AI 에이전트는 데이터 정합성 보정과 반복 리팩터링을 보조했다. 문제 정의, 규칙 설계, 데이터 출처 확인, 테스트 기준 설정, 최종 승인과 병합 결정은 팀원이 담당했다.

## 3. AI 생성 코드의 검증·수정 방식

**AI가 작성했다는 사실만으로 신뢰하지 않는다**는 원칙을 프로젝트 규칙(`CLAUDE.md`)에 명문화했다. 아래 검증 절차는 변경의 성격과 위험도에 맞춰 적용한다.

1. **판정 로직과 생성 로직을 분리한다.** 졸업요건 충족 여부 같은 사실 판정은 규칙 기반 엔진(`graduation_progress.py`)만 하고, LLM은 그 결과를 받아 설명·추천 문장만 만든다. AI가 직접 "졸업 가능 여부"를 판단하지 않도록 아키텍처 단계에서 경계를 그었다.
2. **골든 테스트로 판정 로직 회귀를 고정한다.** 실제 학과 데이터를 근거로 한 시나리오(TC01~TC11)를 `tests/run_golden_tests.py`로 관리한다. 졸업요건·다전공·교육과정 연도·중복 요건 같은 결정론적 로직을 수정할 때는 이 테스트와 관련 단위 테스트를 실행한다.
3. **작성과 검토를 분리한다.** 중요 변경은 작성자와 별도의 검토자가 diff·테스트 결과·실제 동작을 확인한다. 필요할 때 독립 git worktree에서 재현해, 작성자의 설명만으로 병합 여부를 결정하지 않는다.
4. **LLM 프롬프트 변경은 반복 평가한다.** 시스템 프롬프트처럼 LLM 행동에 영향을 주는 변경은 dry-run만으로 완료 처리하지 않는다. 동일 시나리오를 최소 3회 실행하고, 통과 수·실패 유형·지연시간을 함께 확인한다. 네트워크 오류나 API 제한은 모델 품질 실패와 구분해 기록한다.
5. **화면과 배포 환경을 별도로 확인한다.** 가능한 경우 테스트 API 요청과 브라우저 자동화(Playwright)를 사용해 응답뿐 아니라 화면 반영까지 확인한다. 코드·로컬 테스트 통과가 곧 배포 반영을 의미하지 않으므로, 배포 관련 변경은 실제 환경 확인 결과를 별도로 남긴다.
6. **되돌리기 어려운 작업은 먼저 격리 환경에서 검증한다.** DB 마이그레이션·대량 데이터 반영은 가능한 로컬 또는 격리 환경에서 마이그레이션, 시드, 관련 테스트를 먼저 실행한다. 이후 실 환경 반영 여부와 시점은 팀원이 결정한다.
7. **최종 승인은 사람이 한다.** 기본 작업 흐름은 GitHub PR 기반이며, 팀원이 변경 내용과 검증 결과를 확인하고 병합 여부를 결정한다. AI 에이전트는 코드 작성·조사·자체 검증을 보조하지만 저장소와 서비스의 최종 결정권을 갖지 않는다.
8. **MCP로 가져온 외부 데이터도 검증 대상이다.** 디자인 토큰·문서 내용은 조회 시점의 정보일 수 있으므로, 코드·렌더링 결과·최신 팀 결정과 다시 대조한다. MCP가 값을 성공적으로 가져왔다는 사실만으로 제품 반영의 정확성을 보장하지 않는다.
9. **검증 결과를 재현 가능하게 남긴다.** 실행 명령, 대상 브랜치·커밋, 통과·실패 결과와 환경 제약을 PR 또는 변경 기록에 남긴다. 특히 LLM 평가는 모델명, 실행 횟수, 평가 시점, API 제한·네트워크 오류 여부를 함께 기록한다.

LLM에 학생 개인정보를 어떻게 (안) 보내는지는 이 문서의 범위(활용한 AI 도구·범위·검증 방식)를 벗어나는 별도 주제라 README(1.3절)와 [`docs/backend/features/llm-privacy-audit.md`](backend/features/llm-privacy-audit.md)로 옮겼다.
