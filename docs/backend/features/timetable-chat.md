# 시간표 AI 상담 (timetable chat)

이번 학기 실제 개설 분반 중에서 시간 충돌 없는 시간표 조합을 만들어 추천한다.
로드맵 챗과 독립 아키텍처다 (`roadmap_id`가 필요 없다).

- 엔드포인트: `app/api/timetable_agent.py` (`/agent/timetable/*`)
- 에이전트 본체: `app/domains/planning/timetable_chat.py`
- 조합 탐색 기본 요소(충돌 판정·랭킹 지표): `app/domains/planning/timetable.py`

## 역할 분담 — 조합은 규칙 엔진이 짜고, LLM은 설명만 한다

CLAUDE.md 절대원칙 #1과 같은 방향이다. **LLM은 "어떤 과목을 후보로 볼지"만 정한다.**
시간이 겹치지 않는 조합을 실제로 구성하는 건 `build_timetable` 도구 안의 규칙 코드다.

예전에는 조합 구성까지 LLM이 했다 — `list_offered_courses`로 분반 목록을 받아 눈으로
시간을 맞춰보고 `validate_timetable`에 넣어보는 시행착오 방식. 이 방식은 결과가 모델
성능에 그대로 좌우된다. 실계정·실 DB(2026-2학기 3,599분반) 실측:

**Luna(기본값) A/B 실측** — 실 DB(2026-2학기 3,599분반), 프롬프트 2종을 번갈아 돌려
그 응답이 제안한 조합의 최대 학점을 잰 것:

| | n | median | mean | min~max | 12학점 미만 | iterations |
| --- | --- | --- | --- | --- | --- | --- |
| 조합 구성 = LLM | 12 | 12.0 | 11.3 | 0.0~16.5 | 5/12 | 6.5 |
| 조합 구성 = 규칙 엔진 | 8 | **18.0** | 18.1 | 17.0~20.0 | 0/8 | 4.0 |

**96/96쌍 전부 규칙 엔진 쪽이 크다** — 두 분포가 겹치지 않는다(LLM 최대 16.5 <
엔진 최소 17.0). 응답시간도 median 13.8s → 11.1s.

`gpt-4o-mini`로 낮추면 격차가 더 벌어진다: `validate`를 12번 호출해 전부 실패하고
**빈 시간표**로 끝나 사용자 화면에 시간표가 하나도 안 떴다. Luna는 그 정도로 깨지진
않지만 학점을 덜 채운다. **모델 성능에 기대지 않는 게 요점이다.**

측정 한계: 사용자 1명(컴공/데이터사이언스) 기준, 프롬프트가 둘 다 "채워줘" 계열.
"가볍게 6학점만" 같은 요청에는 학점이 지표로서 의미가 없다.

> 챗 품질을 측정할 때는 **실제로 어떤 모델로 돌고 있는지 먼저 확인할 것.** 기본값은
> `app/core/config.py`의 `ROADMAP_AGENT_MODEL`(Luna)이지만 `backend/.env`에 같은 키가
> 있으면 조용히 덮어쓴다. 실행 중 값은 Langfuse trace의 `model` 메타데이터에 남는다.

## 도구

| 도구 | 역할 |
| --- | --- |
| `get_student_context` | 학과·진로·이수기록·학점상한·카테고리별 남은 학점, 그리고 **사용자가 시간표 UI에서 직접 담아둔 강좌**(`current_timetable`) |
| `list_offered_courses` | 이번 학기 개설 과목 검색 (이수구분·학과·전공 스코프) |
| `search_by_career` | 진로 키워드 기반 개설 과목 검색 |
| `check_prereqs` | 선수과목 이수 여부 (best-effort, description 파싱) |
| **`build_timetable`** | **후보 분반 풀 → 시간 충돌 없는 조합 최대 3개.** 시간표 짜기의 기본 도구 |
| `validate_timetable` | 특정 조합 하나가 성립하는지만 확인. 사용자가 "이 조합 되냐"고 콕 집어 물을 때만 |
| `get_roadmap_hint` | 사용자가 로드맵을 언급했을 때만 |
| `finish_response` | 최종 답변 제출 |

## `build_timetable`이 자동으로 처리하는 것

호출자(LLM)가 신경 쓰지 않아도 되게 도구 계층에서 전부 거른다.

- **사용자가 이미 담아둔 강좌를 고정**하고 그 위에 얹는다 (아래 절 참고)
- **같은 과목의 여러 분반 → 과목당 하나만** 선택
- 사용자 요일·시간대 제약 위반 분반 제외 (`_parse_time_constraint`)
- 이미 이수한 과목 제외
- 학점 상한 초과 조합 제외

탐색은 노드 예산(`_MAX_SEARCH_NODES`)이 있는 DFS다. "넣어보기"를 먼저, "건너뛰기"를
나중에 해서 학점을 많이 채우는 조합이 먼저 쌓인다.

### 랭킹은 `timetable._rank_schedules`를 쓰면 안 된다

그 함수는 **요일 수가 1순위**인데, 그건 "같은 과목 집합의 서로 다른 분반 조합"을
비교할 때 맞는 기준이다. 여기서는 과목 수가 다른 조합끼리 비교하므로, 그대로 쓰면
과목 1개짜리(1일)가 4과목 조합(3일)을 제친다 — 실제로 12학점 조합이 가능한 후보
풀에서 3학점짜리 단과목이 1·2위로 나왔다.

(초안이 실제로 그렇게 만들었다가 이 함수를 도입하면서 고쳤다. 기존 챗에는 랭킹 단계
자체가 없었으므로 **출시된 버그는 아니다** — `_rank_schedules`의 유일한 호출자는 별도
규칙 기반 경로인 `timetable.recommend_timetable`이고 거기서는 의도대로 동작한다.)

그래서 `_rank_built_combos`가 `min(학점, 목표학점)`으로 묶어서 정렬한다:

- 목표 미달 조합끼리는 **학점이 많은 쪽**이 위 (최대한 채운다)
- 목표를 채운 조합끼리는 전부 동점 → **요일 수·공백이 적은 쪽**이 위

## 사용자가 시간표 UI에서 직접 담은 강좌 반영

시간표 화면은 `course_plans`/`course_plan_items`에 사용자가 고른 분반을 저장한다
(`app/api/timetables.py`). 챗은 이걸 **이미 확정된 부분**으로 보고 그 위에 얹는다.

- 어느 시간표를 볼지: 요청의 `plan_id`. 프론트(`TimetablePage`)가 지금 열어둔 시간표의
  id를 보낸다. 안 넘어오면 그 학기의 **가장 최근 수정한** 시간표로 폴백한다
  (`_resolve_plan_id`) — 시간표를 여러 개 만들어 비교 중이면 보고 있지 않은 쪽이 잡힐 수
  있어서 프론트가 명시적으로 보내는 게 맞다. 남의 시간표거나 학기가 다르면 무시하고
  백지에서 추천한다 — 여기서 예외를 던지면 챗 자체가 죽는다.
- 담긴 과목은 다시 추천하지 않고, **담긴 강의와 시간이 겹치는 분반은 후보에서 뺀다.**
  안 그러면 사용자가 승인하는 순간 깨진 시간표가 된다.
- 고정분의 학점만큼 상한이 줄어든 상태로 조합을 짠다.
- 응답의 `offering_ids`는 **고정분 + 추가분 전체**다. 담기 API(`POST /me/timetables/
  {plan_id}/items`)가 멱등이라 그대로 적용해도 안전하다. 무엇이 새로 들어가는지는
  `added_offering_ids` / `locked_offering_ids`로 구분해서 내려준다.
- 사용자가 "지금 담은 거 무시하고 처음부터" 라고 하면
  `build_timetable(ignore_current_timetable=true)`.

## 과목 목록은 LLM이 쓰지 않는다

응답 끝에 붙는 과목 목록(`📋 총 N학점` 블록)은 **서버가 DB 값으로 렌더링한다**
(`_render_schedule_summary`). LLM에게 맡기면 과목명과 학점을 지어낸다 — 실측에서
'범주형 및 생존자료 분석'을 '데이터사이언스수학'으로 바꿔 쓰고, 9학점 조합을
15학점이라고 설명했다. 화면에 그려지는 시간표는 `offering_ids`라서 그 순간 설명과
시간표가 어긋난다.

프론트가 최신 추천을 카드로도 그리지만, **대화 기록에는 텍스트만 남는다** — 새로고침
후 "무엇을 추천받았는지"의 유일한 기록이 이 블록이다.

LLM은 왜 이 조합인지·무엇이 부족한지·다음에 뭘 하면 좋은지만 쓴다.

## 가드 (도구 계층에서 강제)

프롬프트에 적어두는 것만으로는 안 지켜지는 것들이라 코드로 되돌린다. 각각 **한 번만**
되돌리고, 되돌림 횟수는 탐색 예산(`MAX_TOOL_ITERATIONS`)에서 빼주지 않는다.

- `schedule_not_engine_approved` — 제출한 조합이 `build_timetable`/`validate_timetable`이
  승인한 조합에 없으면 되돌린다. 예전 가드는 "validate를 한 번이라도 불렀나"만 봐서,
  엔진 결과에서 offering_id를 몇 개 바꿔 끼운 조합이 그대로 통과했다.
- `validated_combo_not_submitted` — 엔진이 조합을 만들어줬는데 `schedules`를 비워서
  끝내려는 경우. UI가 렌더링하는 건 `schedules`라 사용자에겐 아무것도 안 보인다.
- `time_constraint_violation` — 사용자 요일·시간 제약을 어기는 분반이 남아 있는 경우.

반복 상한에 걸려 `finish_response`를 못 부르고 끝났는데 엔진은 이미 성립하는 조합을
만들어둔 경우, 그 조합을 버리지 않고 그대로 응답에 싣는다.
